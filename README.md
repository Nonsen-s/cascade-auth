# Каскад — собственный бэкенд аккаунтов

Самостоятельный сервер регистрации и авторизации на **TypeScript + Fastify + PostgreSQL**. Сервер хранит пользователей, проверяет пароли, выдаёт и отзывает сессии, подтверждает почту и восстанавливает доступ. Supabase и внешняя платформа авторизации не используются. Интерфейс подключён к этому API и может быть заменён отдельно.

Реализованы регистрация, вход/выход, выход со всех устройств, подтверждение и повторная отправка письма, восстановление пароля, HttpOnly-сессии, CSRF/Origin-защита, общие ограничения запросов и надёжная очередь SMTP. Игровой прогресс в этот модуль не входит.

## Запуск в Docker

Нужен запущенный Docker Desktop с Linux Engine. Из корня проекта:

```powershell
npm run docker:setup
npm run docker:up
```

`docker:setup` создаёт приватный `.env.docker` со случайными ключами и паролем базы. Существующий файл не перезаписывается. Для запуска нужны Node.js 22.12+, npm, Docker и `tar` (входит в современные Windows и обычные Linux-дистрибутивы); устанавливать зависимости проекта для Docker не требуется.

`docker:build` и `docker:up` передают разрешённые рабочие файлы как [архив контекста Docker](https://docs.docker.com/build/concepts/context/#local-tarballs). Это позволяет собирать проект и из текущей папки с кириллицей, обходя обнаруженную ошибку BuildKit в заголовке `x-docker-expose-session-sharedkey`. Команда `docker:up` сначала собирает оба образа, затем запускает Compose и ждёт готовности.

- Сайт и API через общий адрес: [http://127.0.0.1:8080](http://127.0.0.1:8080).
- Локальный почтовый ящик: [http://127.0.0.1:8025](http://127.0.0.1:8025).
- Готовность API: [health/ready](http://127.0.0.1:8080/health/ready).
- Контракт API: [OpenAPI](http://127.0.0.1:8080/api/openapi.json).

После регистрации откройте письмо в Mailpit, подтвердите почту и установите пароль. Mailpit принимает письма локально; интернет-доставки в этой конфигурации нет.

[compose.yaml](compose.yaml) запускает PostgreSQL 17, Mailpit, отдельный этап миграций, API и Nginx со статической сборкой интерфейса. API ждёт успешных миграций, Nginx — готовности API. Наружу на localhost опубликованы только 8080 и 8025; база и SMTP доступны внутри Compose. Порядок зависимостей основан на [проверках готовности Compose](https://docs.docker.com/compose/how-tos/startup-order/).

```powershell
npm run docker:status
npm run docker:down
```

Остановка сохраняет базу в именованном томе `cascade-auth-local_postgres-data`. Docker использует новую отдельную базу: прежние `.local/postgres`, `.local/mail` и `.env.server` остаются на месте. Для других портов задайте `WEB_PORT` и `MAILPIT_PORT` перед первым `docker:setup`; при ручной смене `WEB_PORT` обновите также `APP_ORIGIN` в `.env.docker`.

Compose предназначен для локальной разработки: HTTP, Mailpit, роль владельца локальной базы и `NODE_ENV=development`. Образ API по умолчанию имеет `NODE_ENV=production`; требования production приведены ниже. API и Nginx работают без root с файловой системой только для чтения и временным `/tmp`. Образы API содержат собранный JavaScript, миграции и runtime-зависимости; исходники, тесты, приватные настройки и карты исходников туда не копируются.

## Локальный запуск

Нужен Node.js 22.12+; проверка выполняется с Node.js 24.14.1.

```powershell
npm ci
npm run server:setup
npm run server:dev
```

`server:setup` создаёт игнорируемый Git файл `.env.server` со случайными приватными ключами и никогда не перезаписывает существующую конфигурацию. Сервер запускается на [http://127.0.0.1:3001](http://127.0.0.1:3001/health/ready). Контракт API: [OpenAPI](http://127.0.0.1:3001/api/openapi.json).

Локальный режим использует настоящий встроенный PostgreSQL **PGlite** с постоянными данными в `.local/postgres`. Это явный режим разработки с теми же миграциями и SQL-репозиториями, а не подмена авторизации. Production-конфигурация запрещает PGlite.

Письма разработки сохраняются в `.local/mail/*.json`: поле `text` содержит ссылку подтверждения или восстановления. После регистрации откройте соответствующий файл, перейдите по ссылке и установите пароль. Подтверждение выдаёт только ограниченную сессию установки пароля; пароль, введённый до подтверждения почты, становится недействительным. Каталог — локальный почтовый ящик, HTTP-доступа к нему нет; он исключён из Git и Docker context. Production использует SMTP и запрещает файловый транспорт.

Для имеющихся форм откройте второй терминал:

```powershell
npm run dev
```

Адрес: [http://127.0.0.1:5173](http://127.0.0.1:5173/). Он должен совпадать с `APP_ORIGIN` в `.env.server`. Cookie сессии сохраняется браузером после обновления страницы. Клиент не хранит токены в localStorage/sessionStorage.

## Состав для GitHub

В Git остаются рабочие исходники, общие схемы, миграции, конфигурация сборки, lockfile, Docker, скрипты запуска, CI и документация API. `.dockerignore` разрешает передавать в сборку только необходимые исходники и конфигурацию.

Тесты и их настройки сохранены в `local-only/qa`, старые скриншоты, результаты проверок и исторические документы — в `local-only/archive`. Эта папка исключена из Git и Docker. Локальные данные, `.env*` с секретами, `node_modules`, кэши и результаты сборки также исключены; шаблоны `.env.server.example` и `.env.docker.example` публикуются.

## Структура и публичный API

```text
server/src/domain/          Модели, назначения токенов, сроки действия, ошибки
server/src/application/     AccountService и небольшие контракты зависимостей
server/src/infrastructure/  PostgreSQL, Argon2id, криптография, SMTP и очередь
server/src/http/            REST, сессии cookie, CSRF, HTTP-ошибки, OpenAPI
server/src/runtime.ts       Сборка зависимостей и завершение работы
server/migrations/          Версионируемые SQL-миграции с контрольными суммами
shared/auth-contract.ts     Общие схемы запросов и ответов, без секретов
src/infrastructure/http/    Браузерный адаптер собственного API
```

Подробности с примерами независимых изменений: [архитектура](docs/backend-architecture.md). Контракт для нового дизайна и любого другого клиента: [API v1](docs/api.md).

`AccountService` зависит от операций репозитория, хеширования, токенов и часов; он не знает об HTTP, React, SMTP или SQL. Транзакции находятся в SQL-адаптере. Компоненты вызывают прикладные операции через HTTP-адаптер и не обращаются к базе. Классы выражают зависимости и состояние, а правила ввода представлены общими чистыми схемами.

## Production

1. Создайте PostgreSQL и SMTP, задайте точный HTTPS `APP_ORIGIN`, случайный 32-байтный `APP_SECRET`, отдельный ключ шифрования почты и доступы в окружении сервера. Пример настроек — `.env.server.example`; секреты нельзя записывать в `VITE_*`.
2. Задайте `NODE_ENV=production`, `DB_DRIVER=postgres`, `MAIL_TRANSPORT=smtp`, `AUTO_MIGRATE=false`, `SMTP_ALLOW_PLAINTEXT=false`. Для TLS PostgreSQL используйте `DATABASE_SSL=true` с доверенным сертификатом; дополнительный CA передавайте через `NODE_EXTRA_CA_CERTS` при запуске Node. SSL-параметры URL (`ssl*`, `uselibpqcompat`) запрещены для `DATABASE_URL` и `MIGRATION_DATABASE_URL`: флаг `DATABASE_SSL` имеет единственный приоритет и не переопределяется `PGSSLMODE`. Настройте TLS на reverse proxy и точные адреса/CIDR его узлов в `TRUST_PROXY`; по умолчанию forwarded-заголовки не считаются доверенными.
3. Примените `npm run server:migrate` отдельным этапом развёртывания. Для миграций можно передать `MIGRATION_DATABASE_URL` владельца схемы, оставив `DATABASE_URL` приложения с меньшими правами.
4. Выполните `npm run server:build`, затем `npm run server:start`. Сервер можно развернуть независимо от React. Образы: `npm run docker:build`; после миграции — `docker run --env-file .env.server -p 127.0.0.1:3001:3001 cascade-auth-api:local`. Установите `HOST=0.0.0.0` внутри контейнера и используйте доступные контейнеру адреса PostgreSQL/SMTP.
5. Разместите `/api` за reverse proxy того же сайта. Для интерфейса настройте SPA fallback на `index.html`, включая `/auth/confirm`. Cookie в production получают Secure/HttpOnly/SameSite и префикс `__Host-`.
6. Настройте SPF/DKIM/DMARC у почтового провайдера, подтвердите отправителя и отключите переписывание одноразовых ссылок. Доставка внешнему адресу зависит от SMTP и DNS; локальные тесты не доказывают интернет-доставку.

Для runtime-роли PostgreSQL достаточно USAGE схемы accounts, SELECT/INSERT/UPDATE/DELETE её прикладных таблиц и SELECT schema_migrations. Владение схемой, CREATE/ALTER/TRUNCATE и миграционные права приложению не нужны. Публичный доступ к схеме и таблицам отозван миграцией. Миграции следует выполнять ролью владельца, runtime-подключение — отдельной ролью.

Все экземпляры API используют общие APP_SECRET и набор почтовых ключей. Ключи почты задаются объектом `MAIL_ENCRYPTION_KEYS={"v1":"64-hex", "v2":"64-hex"}` и `MAIL_ACTIVE_KEY_ID=v2`. Старый ключ сохраняйте до обработки или истечения всех его заданий; затем удалите. Смена APP_SECRET требует обновления CSRF-доказательств клиентами.

Обычная сессия действует 14 дней, одноразовая ссылка подтверждения — 24 часа, восстановления — 1 час, recovery-cookie — 15 минут. Повторная отправка подтверждения и восстановление имеют раздельные минутные интервалы; дополнительные лимиты IP и адреса действуют в общей базе. Политики находятся в `domain/models.ts` и `http/auth-context.ts`, а не разбросаны по обработчикам.

После подтверждения почты клиент получает recovery-cookie, запрашивает CSRF-доказательство через `/session`, затем вызывает `/reset-password` для завершения регистрации. JSON-ответ подтверждения сохраняет прежний формат `{ message }`. Запрос нового письма восстановления не отзывает уже начатую recovery-сессию; её заменяет только погашение новой действительной ссылки либо успешная установка пароля.

## Масштабирование и эксплуатация

API не требует sticky sessions: сессии, счётчики и очередь общие в PostgreSQL. Начальный пул — 10 подключений на экземпляр; ограничьте сумму пулов относительно PostgreSQL. `HASH_CONCURRENCY` ограничивает память Argon2, по умолчанию 2 операции и до 8 ожидающих задач.

После подтверждённого rollback при SQLSTATE `40P01` PostgreSQL-адаптер повторяет транзакцию не более двух раз. Callback транзакции выполняет только SQL и локальные вычисления: внешние побочные эффекты нужно отправлять через outbox. Ошибки сети, других типов и ошибки после начала `COMMIT` не повторяются.

Небольшое развёртывание запускает почтовый обработчик внутри API. Чтобы масштабировать его отдельно, задайте API `RUN_MAIL_WORKER=false`, а на PostgreSQL/SMTP запустите `npm run server:worker` или `node server/dist/worker.js`. Несколько обработчиков используют аренду заданий и `SKIP LOCKED`. Отдельный обработчик с PGlite не допускается: локальная база принадлежит одному процессу.

`/health/live` проверяет процесс, `/health/ready` — базу. SIGTERM завершает текущие запросы, обработчик и пул. Логи содержат ID запроса, маршрут, статус и безопасные причины ошибок; пароли, cookie и query string не пишутся. Для наблюдения за почтой отслеживайте задания `accounts.email_outbox` с failed=true и предупреждения SMTP. После исправления ключей или SMTP задание можно вернуть в работу, сбросив failed/attempts/lease и available_at, если ссылка ещё не истекла.

Доставка SMTP — как минимум один раз. При сбое после успешной передачи, но до фиксации результата возможно повторное письмо с тем же Message-ID. Одноразовый токен не срабатывает дважды. Истёкшие сессии, ссылки и счётчики удаляются пакетами. Резервные копии PostgreSQL и ключи шифрования нужно сохранять раздельно и проверять их восстановление.

## Проверки

```powershell
npm ci
npm run check
```

`check` проверяет типы рабочих исходников, ESLint, форматирование и обе сборки. Публикуемый CI дополнительно проверяет Compose, сборку обоих образов и зависимости runtime. Тесты в GitHub не загружаются и в CI не запускаются.

Сохранённые локальные проверки запускаются из корня:

```powershell
npm run check:local
npm run test:e2e
```

Отдельно доступны `npm test`, `npm run test:server`, `npm run typecheck:qa` и `npm run test:watch`. Для установленного Chrome перед E2E задайте `$env:PLAYWRIGHT_CHANNEL='chrome'`; иначе установите браузер командой `npx playwright install chromium`. Результаты, тестовые базы и письма сохраняются внутри `local-only/qa/artifacts`.

По умолчанию серверные тесты используют отдельный PGlite. Для PostgreSQL нужна выделенная база с именем, заканчивающимся на `_test`, переменная `TEST_POSTGRES_URL` и явное разрешение `TEST_POSTGRES_ALLOW_RESET=true`: тесты очищают её прикладные таблицы. Рабочую базу использовать нельзя.

В чистом клоне без `local-only/qa` команды тестирования сообщают об отсутствии локального набора и завершаются с ошибкой. `npm run check` и Docker от этой папки не зависят. Прежний отчёт проверок сохранён локально в `local-only/archive/docs/verification.md`.
