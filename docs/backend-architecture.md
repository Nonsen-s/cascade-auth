# Устройство собственного бэкенда

Сервер — модульный монолит на TypeScript и Fastify. Его можно запускать отдельно от интерфейса. PostgreSQL — единственное общее хранилище пользователей, сессий, ограничений запросов и очереди писем. Supabase не используется.

## Ответственность модулей

| Модуль                                                      | Ответственность                                                                                                                   |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `shared/auth-contract.ts`                                   | Форматы входа и ответа API, правила почты и пароля. Совместно используется сервером и клиентом, секретов и серверных импортов нет |
| `server/src/domain`                                         | Типы аккаунта, назначения токенов, сроки действия, ошибки предметной области                                                      |
| `AccountService` (`server/src/application/auth-service.ts`) | Регистрация, проверка пароля, подтверждение, восстановление, вход и отзыв сессий через небольшие контракты                        |
| `server/src/infrastructure/database`                        | SQL, транзакции, миграции, пул PostgreSQL и явный локальный адаптер PGlite                                                        |
| `server/src/infrastructure/security`                        | Argon2id, случайные токены, CSRF/HMAC, шифрование писем с ротацией ключей                                                         |
| `server/src/infrastructure/mail`                            | SMTP, локальный почтовый ящик разработки, обработчик очереди                                                                      |
| `server/src/http`                                           | Cookie, Origin/CORS/CSRF, HTTP-коды и версия REST API, OpenAPI                                                                    |
| `server/src/runtime.ts`                                     | Сборка зависимостей и освобождение ресурсов                                                                                       |

`AccountService` не импортирует Fastify, PostgreSQL, SMTP, React или DOM. В него передаются `AuthRepository`, `PasswordHasher`, `TokenIssuer` и часы. Замена SMTP не меняет регистрацию; настройка хеширования не меняет HTTP; новый интерфейс использует тот же REST API. Наследование и общий контейнер зависимостей не нужны: зависимости соединяются явно.

Классы хранят реальные зависимости и состояние: `Argon2PasswordHasher` ограничивает одновременно работающие задачи, `MailWorker` управляет доставкой и остановкой, `PostgresAuthRepository` реализует транзакционные операции агрегата аккаунта. Доменные модели остаются простыми неизменяемыми типами. Ошибки приводятся к одному публичному формату на HTTP-границе.

## Сессии

Cookie содержит 256-битный случайный идентификатор; база — только его SHA-256. Пароли хешируются Argon2id: 64 MiB, 3 прохода, 1 линия, отдельная случайная соль. Отсутствующий аккаунт проходит реальную проверку фиктивного хеша, чтобы дешёвая ветка входа не выдавала его существование. Одновременно выполняются не более двух операций хеширования по умолчанию, очередь ограничена восемью задачами.

Сессия действует 14 дней, recovery-сессия — 15 минут. Recovery-сессия не авторизует `/me`. После восстановления пароля все прежние сессии и ссылки отзываются, а текущему браузеру выдаётся новая сессия. На аккаунт оставляется до 20 обычных сессий. Сессия проверяется в общей базе и немедленно перестаёт работать после отзыва; локальные JWT и список их отзыва не требуются.

В production cookie получает `Secure`, `HttpOnly`, `SameSite=Lax`, префикс `__Host-`, `Path=/` и не содержит Domain. Секрет сессии недоступен JavaScript. CSRF-доказательство выдаётся отдельно и связано с конкретной сессией через HMAC. Для изменений обязательны точный Origin, JSON и, для операций с действующей сессией, `X-CSRF-Token`. CORS разрешает один настроенный origin. Доверие к proxy по умолчанию отключено.

Сервер определяет пользователя по cookie и базе, не по переданным `email`, `userId` или состоянию страницы. Для чтения чужих пользователей нет публичного маршрута. Прямого подключения клиента к базе нет; доступ к таблицам для PostgreSQL PUBLIC отозван. В этой схеме граница доступа реализуется сервером, а не клиентскими RLS-политиками.

## Транзакции и гонки

Создание аккаунта и постановка письма в очередь — одна транзакция. Повторная регистрация не меняет пароль, ID или состояние существующего аккаунта. Ответ для занятого адреса общий.

Одноразовые ссылки содержат случайный токен; в таблице хранится его хеш. Ссылки подтверждения действуют 24 часа, восстановления — 1 час. Назначение проверяется отдельно. Повторная отправка заменяет старую ссылку. Погашение выполняется после блокировки строки аккаунта, поэтому две параллельные попытки не используют одну ссылку дважды.

Подтверждение почты атомарно отключает пароль, заданный до доказательства владения адресом, увеличивает `auth_version`, погашает ссылки и выдаёт только recovery-сессию установки пароля. Отключённый пароль заменяется Argon2-хешем независимого случайного секрета, который не возвращается клиенту и не связан с почтовым токеном или cookie. Владелец устанавливает свой пароль существующим `/reset-password` с CSRF, после чего получает access-сессию. Повторный анонимный запрос письма не отзывает уже выданную recovery-сессию; отзыв происходит при погашении новой действительной ссылки или смене пароля.

`auth_version` защищает вход от гонки со сменой пароля: Argon2 выполняется вне транзакции, затем сервер блокирует пользователя и повторно проверяет версию перед созданием сессии. Сброс пароля блокирует тот же аккаунт, увеличивает версию, меняет хеш и отзывает старые права одной транзакцией.

Взаимные переключения двух аккаунтов могут вызвать PostgreSQL deadlock при отзыве прежних сессий и ограничении их числа. Адаптер повторяет SQL-callback не более двух раз только после подтверждённого rollback и SQLSTATE `40P01`. После начала `COMMIT`, при сетевой ошибке или неуспешном rollback повтор запрещён. Внешние побочные эффекты не выполняются в таком callback; письма передаются через транзакционный outbox.

## Письма и рост нагрузки

Очередь — таблица PostgreSQL. Письмо шифруется AES-256-GCM до записи, поскольку содержит bearer-ссылку. Ключи хранятся вне базы; их идентификаторы позволяют дочитать старые задания при ротации.

Несколько обработчиков выбирают задания с `FOR UPDATE SKIP LOCKED`. У каждого задания есть владелец и аренда на 2 минуты. При падении процесса аренда истекает и письмо забирается снова. Ошибки SMTP приводят к отложенным попыткам, после восьми попыток требуется внимание оператора. Нерасшифровываемые задания сохраняются с признаком ошибки. После успешной доставки зашифрованное содержимое удаляется.

Доставка SMTP выполняется как минимум один раз: сбой между успешным SMTP и фиксацией результата может дать повторное письмо. Повтор использует тот же Message-ID, а ссылка остаётся одноразовой. Сервер не обещает недостижимую «ровно одну доставку» внешнему SMTP.

Ограничения запросов используют атомарные счётчики PostgreSQL, одинаковые для всех API-процессов. Ключи адресов и IP псевдонимизируются HMAC. Истёкшие записи удаляются ограниченными пакетами. Redis, брокер сообщений и микросервисы не требуются. При росте можно отдельно увеличивать число API и SMTP-обработчиков, а лимит пулов выбирать относительно возможностей PostgreSQL.

## Следующие модули

Будущие игровые данные нужно связывать с UUID аккаунта. Игровой маршрут получает пользователя после проверки обычной сессии; recovery-cookie для него непригоден. Награды, покупки и рейтинг требуют собственных серверных правил. Добавление игровых режимов не меняет регистрацию и хранение сессий.

Для внешних способов входа следует добавить таблицу идентичностей с уникальной парой провайдер/subject и отдельную операцию привязки после проверки владения обеими идентичностями. Самостоятельное объединение аккаунтов по введённой почте не предусмотрено.
